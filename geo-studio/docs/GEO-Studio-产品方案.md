# GEO Studio 产品方案

> 一个面向企业品牌的生成式引擎优化（GEO）自动化平台：把品牌断言转化为可实测、可生产、可分发、可追踪的完整 GEO 运营闭环。

---

## 一、产品概述

### 背景与问题

用户越来越习惯直接向 ChatGPT、Claude、Gemini、Perplexity 以及国内的豆包、Kimi、元宝、文心等生成式引擎提问，而不是翻搜索结果。这意味着品牌的"第一印象"正从搜索排名，转移到 AI 答案里的"是否被提及、是否被准确复述、是否被优先引用"。传统 SEO 工具优化的是排名与点击，无法回答"AI 在推荐谁、怎么描述我"这个新问题。

企业目前的 GEO 工作高度依赖人工：手动去各引擎逐题测试、用表格记录、凭经验写内容、分散地发到各渠道，既不可量化也无法持续。GEO Studio 要解决的，就是把这套高价值但重复的工作产品化、自动化。

### 一句话定位

GEO Studio 是企业品牌的"AI 可见度运营中台"——从诊断、内容生产到分发与监测，管理品牌在生成式引擎中的可信度资产。

### 目标用户

核心用户是企业的品牌 / 市场 / 内容运营团队，以及服务多个客户的营销与公关代理机构。次要用户是关注 AI 渠道获客的增长团队。

### 价值主张

平台把 GEO 的四件核心工作连成闭环：客观诊断品牌在 AI 中的现状基线；按语义矩阵系统化生产 AI 友好的内容；把内容分发到高权重信源；持续监测可见度指标并对错误信息告警。最终交付的不是一次性方案，而是一条能看涨跌的"AI 可见度"运营曲线。

---

## 二、产品定位与差异化

与传统 SEO 工具相比，GEO Studio 优化的对象是"被 AI 引用与复述"，而非搜索排名，核心指标是答案份额与提及率，而非关键词排名。

与通用 AI 写作工具相比，GEO Studio 的内容生产是被"诊断结果 + 语义矩阵 + 信源策略"驱动的，目标是"被 AI 摘取"，而非单纯产出文章。

与人工咨询 / 代运营相比，GEO Studio 把方法论沉淀成可复用、可量化、可持续的系统，把人从重复劳动中释放出来，专注于策略判断与内容审核。

护城河主要在三处：沉淀下来的 GEO 方法论引擎（诊断与评分的提示词体系）、多引擎实测的工程能力、以及长期积累的品牌可见度时序数据。

## 三、核心功能模块

### 1. 品牌与实体管理

维护品牌的"唯一真相源"：统一的名称、一句话定义、核心断言、业务定位、关键数据、资质背书。这是所有下游模块的输入，也是对外保持信息一致、帮助 AI 正确识别品牌实体的基础。支持多品牌 / 多租户。

### 2. 诊断与多引擎实测

基于品牌信息自动生成诊断问题集（类目级、对比级、品牌级、属性级四类），一键派发到接入的 AI 引擎实际作答，再由评分流水线自动分析每条回答：是否提及、提及位置、信息准确性、情感倾向、竞品对比、引用来源。结果汇总为可见度基线（提及率、正面率、答案份额等），并支持定时复测，形成趋势。

### 3. 语义矩阵与内容生产

按"用户意图 × 内容角度"生成语义矩阵，规划品牌应覆盖的内容版图，并依据诊断结果标记优先缺口。每个矩阵格子可一键生成 AI 友好的内容初稿（结论前置、结构化、含可引用事实、数据占位提醒）。内容进入内容库统一管理状态（草稿 / 审核 / 已发布）。

### 4. 信源分发管理

生成信源分发矩阵：按信源权重金字塔（共识层 / 专业层 / 社区层 / 自有阵地）规划每类内容铺向哪些具体信源、用什么形态、什么优先级。对接官方发布接口的渠道支持自动 / 半自动发布；无官方接口的渠道生成标准发布稿，走人工分发。

### 5. 监测、趋势与告警

把诊断指标按时间快照存入时序库，绘制可见度趋势曲线；监测 AI 答案中关于品牌的错误信息并告警，辅助定位是哪个信源在污染答案；跟踪竞品在同一问题集上的表现做横向对标。

### 6. 协作与审核

团队角色与权限：内容运营、策略分析、发布审核、管理员。内容发布前可配置审核流，确保对外信息准确合规。

## 四、系统架构

平台采用分层架构，请求自上而下流动，重活（生成、实测、发布、爬取）全部异步化。

**前端层**：React Web 应用，包含工作台、可见度看板、内容编辑器与设置。

**API 网关与鉴权层**：统一入口，处理多租户、鉴权、权限与审计。

**核心服务层**：拆分为品牌实体服务、诊断实测服务、内容矩阵服务、分发监测服务，各自独立演进。

**AI 编排层**：整个平台的"大脑"。包含 LLM 路由（统一调度 Claude 等模型）、生成与评分流水线（内容初稿、回答打分）、以及 RAG 检索（让生成与评分基于品牌真实资料与检索结果）。提示词体系作为可版本化的资产在这里集中管理。

**集成连接器层**：平台的核心难点与护城河，分两类连接器。引擎连接器负责把诊断问题派发到各 AI 引擎并取回答案；发布连接器负责通过各平台官方接口发布内容。这一层的可行性与稳定性直接决定产品的能力边界，详见第六、七节。

**异步调度层**：任务队列 + 定时调度 + Worker 集群。实测、生成、发布、监测爬取都作为异步任务执行，定时复测由调度器驱动。

**数据层**：关系库（品牌、内容、任务、发布记录）、时序指标库（可见度指标快照，支撑趋势）、向量库（语义检索与 RAG）、对象存储（内容与素材）、缓存。

### 技术选型建议

| 层 | 选型方向 |
|---|---|
| 前端 | React + TypeScript，组件化看板与编辑器 |
| 后端服务 | Node.js / NestJS 或 Python / FastAPI，按服务边界拆分 |
| AI 编排 | LLM 网关统一封装模型调用、重试、配额、提示词版本管理 |
| 异步任务 | 消息队列（如 BullMQ / Celery）+ 定时调度 |
| 关系库 | PostgreSQL |
| 时序指标 | 时序库或 PG + 时间维表 |
| 向量检索 | 向量数据库（pgvector / 专用向量库） |
| 对象存储 | S3 兼容存储 |
| 可观测 | 日志、指标、链路追踪、审计 |

## 六、多引擎实测的实现路径（含可行性说明）

"一键测多家引擎"是产品的核心卖点，但不同引擎的接入难度差异极大，需要分层处理，并对客户如实标注每种方式的性质。

**路径 A — 官方 API（最稳）**：部分引擎或其企业版提供可调用的问答 / 检索接口。优先走官方接口，稳定、合规、可规模化。

**路径 B — 代理引擎评估（当前可立即落地）**：以一个具备联网检索能力的大模型作为"代理引擎"，模拟检索增强型 AI 的作答，再做评分。这是当前原型已验证、可立即上线的方式，能产出有效的相对基线与趋势，但需明确告知客户它是"近似评估"，不等同于在目标引擎上的真实结果。

**路径 C — 无官方接口的引擎**：对没有开放接口的引擎，可考虑受控的浏览器自动化或合规的第三方数据服务获取答案。务必评估目标平台的服务条款与稳定性风险，作为补充而非主力，并对结果标注来源与时效。

工程上，所有引擎接入抽象为统一的"引擎连接器"接口（输入问题、输出答案与来源），上层评分流水线与引擎无关，新增引擎即新增一个连接器。这样能力可以随商务与工程进展逐步扩展，而不影响产品主流程。

## 七、发布自动化的实现与合规边界

发布能力同样按平台的开放程度分级，原则是**只走官方接口、只做平台允许的自动化、绝不收集平台账号密码、敏感渠道一律人工把关**。

| 渠道 | 自动化程度 | 方式 |
|---|---|---|
| 自有官网 / CMS（如 WordPress） | 完全自动 | 官方 API / OAuth，最优先 |
| 微信公众号（认证服务号） | 半自动 | 官方素材与发布接口，需认证主体 |
| 微博 | 半自动 | 开放平台 API，有申请门槛 |
| 知乎 / 小红书 | 不自动 | 无开放发布接口，导出发布稿 + 人工 |
| 百科 / 第三方榜单 | 不自动 | 走平台编辑流程，人工提交 |

授权统一走 OAuth，平台侧只保存授权令牌而非账号密码。对不可自动发布的渠道，平台生成排版就绪的发布稿，把"最后一步发布"留给人工——这既是合规要求，也对内容质量与品牌安全更稳妥。

需要强调：平台生成的所有内容都应经人工审核后发布，且不得用于伪造数据、虚假宣传或操纵评价；产品内置审核流，正是为了守住这条底线。

## 八、监测与指标体系

平台围绕一组核心指标构建可见度看板，并按时间持续快照以呈现趋势：

提及率（品牌在目标问题集中被提及的比例）、引用率（品牌内容被 AI 作为来源引用的比例）、答案份额（在对比类问题中品牌相对竞品的占比，作为北极星指标）、情感分布、信息准确率、竞品对标。

在此之上有两类主动能力：定时复测驱动趋势曲线，让运营动作的效果可被衡量；错误信息告警在监测到 AI 复述了关于品牌的错误事实时触发，并辅助回溯是哪个信源造成的，以便去源头修正。

## 九、用户角色与权限

管理员负责租户、成员与渠道授权管理；策略分析负责诊断、解读指标、规划语义矩阵与分发优先级；内容运营负责生成与编辑内容、提交发布；发布审核负责对外内容的最终把关。代理机构场景下，支持按客户隔离的多品牌工作区。

## 十、实施路线图

| 阶段 | 周期 | 范围 |
|---|---|---|
| MVP | 0–3 月 | 在现有原型基础上补齐后端与持久化：多品牌管理、代理引擎实测 + 定时复测、语义矩阵与初稿生成、自有 CMS 自动发布、基础可见度看板 |
| V1 | 3–6 月 | 接入 2–3 个主流引擎、公众号 / 微博官方发布、可见度趋势追踪、错误信息告警、团队协作与审核流 |
| V2 | 6–12 月 | 信源 / 实体图谱管理、自动化分发工作流、竞品持续监测、更多引擎与平台、对外开放 API |

MVP 的目标是把当前可用的单引擎闭环工程化、可商用；V1 补齐多引擎与正式发布；V2 走向平台化与生态化。

## 十一、商业模式（示意）

| 套餐 | 面向 | 关键额度 |
|---|---|---|
| Starter | 单品牌团队 | 1 品牌、代理引擎实测、低频复测、自有渠道发布 |

定价维度建议围绕品牌数、接入引擎数与实测频次、团队席位、发布渠道、是否私有化展开。

## 十二、风险与合规

平台条款风险：发布与数据获取必须以各平台官方接口和服务条款为边界，敏感渠道坚持人工，避免违规自动化导致封号。

内容真实性风险：AI 生成内容存在幻觉，所有对外内容须经人工审核；平台明确禁止用于伪造数据或虚假宣传，并以审核流加以约束。

引擎接入稳定性风险：非官方接入方式不稳定且受平台政策影响，应作为补充并对结果标注性质与时效。

数据隐私风险：品牌资料与授权令牌属敏感数据，需加密存储、最小权限访问、完整审计，授权只存令牌不存密码。

---

## 十三、成功指标

产品层面的北极星指标，是客户品牌在其目标问题集上的**答案份额 / 提及率的持续提升**——即平台是否真的让品牌在 AI 世界里更被看见、被准确复述。围绕它的支撑指标包括：客户可见度曲线的正向斜率、内容从生产到分发的周转效率、错误信息从发现到修正的时长，以及客户留存与多品牌扩展率。
